## 1. 背景与目标

项目已经具备按知识库隔离的文档 RAG、流式聊天和 `prompts.py` 中预置的 GraphRAG、NL2SQL、多通道融合提示词，但后端尚未实现这些提示词对应的执行链路。

本次新增最小可用的三类检索通道：

1. `document`：复用当前 Milvus 文档检索链路；
2. `graph`：实体抽取、NL2Cypher、Neo4j 只读查询；
3. `sql`：NL2SQL、PostgreSQL 只读运营数据查询。

Chat 请求通过 `channels` 指定通道。传入一个通道时执行单通道回答；传入多个通道时用 `asyncio.gather()` 并发检索，再使用 `FUSION_PROMPT` 合成回答。

## 2. 已确认的数据来源

### 2.1 NL2SQL 运营表

`NL2SQL_PROMPT` 定义的以下表将由脚本实际创建在现有 PostgreSQL `rag` 数据库中：

- `categories`；
- `products`；
- `customers`；
- `orders`；
- `order_items`。

这些表用于演示和验证 NL2SQL 流程，不替代现有知识库业务表。

### 2.2 Neo4j 医疗图谱

图谱节点和关系严格遵循 `NL2CYPHER_PROMPT`：

- 节点：`Disease`、`Symptom`、`Drug`、`Department`、`Check`、`Food`；
- 关系：`HAS_SYMPTOM`、`BELONGS_TO`、`COMMON_DRUG`、`RECOMMEND_DRUG`、`NEED_CHECK`、`DO_EAT`、`NO_EAT`、`ACOMPANY_WITH`。

脚本会创建约束并导入少量演示数据。所有演示节点、关系和属性将注明仅用于验证 GraphRAG 流程，不作为医疗诊断、处方或治疗依据。

## 3. API 契约

### 3.1 Chat 请求扩展

现有 `ChatRequest` 增加字段：

```python
channels: list[Literal["document", "graph", "sql"]]
```

默认值为：

```json
["document"]
```

约束：至少一个通道、最多三个通道、通道名称不重复。已有前端不传该字段时保持原有文档 RAG 行为。

### 3.2 兼容性

- `POST /api/v1/chat` 保持原路径，返回完整回答；
- `POST /api/v1/chat/stream` 保持 SSE 协议，按模型生成片段返回；
- 两个接口均接受 `channels`；
- 本次不新增独立 Graph、SQL 或 Fusion HTTP 路由。

## 5. 通道执行与融合

### 5.1 文档通道

复用 `search_docs_raw()`，按 `knowledge_base_id` 检索和重排。结果经 `format_doc_context()` 转为文档证据文本，来源保留为文档名称，不包含页码、分块序号或相似度。

### 5.2 图谱通道

图谱通道执行顺序：

```text
ENTITY_EXTRACT_PROMPT
  -> JSON 实体
  -> NL2CYPHER_PROMPT
  -> 只读 Cypher 校验
  -> Neo4j 查询
  -> 原始图谱证据
```

生成 Cypher、解析实体、校验或 Neo4j 查询任一异常时，完整链路最多重试一次。第二次仍失败时记录警告并将该通道标记为无可用证据；多通道模式不阻塞其他通道。

Cypher 安全规则：

- 只接受以 `MATCH` 或 `OPTIONAL MATCH` 开始的单条语句；
- 禁止 `CREATE`、`MERGE`、`DELETE`、`SET`、`REMOVE`、`CALL`、`LOAD CSV`；
- 无 `LIMIT` 时追加 `LIMIT 20`；显式 `LIMIT` 不得超过 20；
- 仅作为当前 Neo4j 演示图谱的只读查询。

### 5.3 SQL 通道

SQL 通道执行顺序：

```text
NL2SQL_PROMPT
  -> SQL 清理与只读校验
  -> PostgreSQL 查询
  -> 原始运营数据证据
```

生成 SQL、校验或执行任一异常时，完整链路最多重试一次。第二次仍失败时记录警告并将该通道标记为无可用证据。

SQL 安全规则：

- 只接受单条 `SELECT`；
- 禁止分号拼接和写入/DDL 关键字；
- `FROM`、`JOIN` 只允许访问五张运营演示表；
- 无 `LIMIT` 时追加 `LIMIT 100`；显式 `LIMIT` 不得超过 100；
- 不允许复杂多层子查询，和 prompt 约束保持一致。

### 5.4 多通道

`channels` 长度大于一时：

```python
results = await asyncio.gather(
    *(retrieve_channel(channel) for channel in channels),
    return_exceptions=True,
)
```

成功通道的证据以明确来源分段拼接后传给 `FUSION_PROMPT`。如果部分通道失败，仍使用其他成功通道融合；如果全部没有证据，返回统一的无相关信息提示。

单通道时分别使用：

- 文档：`DOC_QA_PROMPT`；
- 图谱：`GRAPH_QA_PROMPT`；
- SQL：`SQL_QA_PROMPT`。

## 6. 演示初始化脚本

### 6.1 运营表脚本

`init_operational_tables.py` 使用项目 `DATABASE_URL` 创建表、索引和少量商品/订单演示数据。脚本采用 `CREATE TABLE IF NOT EXISTS` 与冲突忽略式写入，可重复运行。

### 6.2 图谱脚本

`init_medical_graph.py` 使用 Neo4j 配置创建节点名称唯一约束，并从 `medical_graph_demo.json` 用 `MERGE` 导入演示数据。该 JSON 文件可审阅、可替换，避免将演示数据硬编码在业务查询模块中。

## 8. 非目标

本次不实现：

- 自动识别用户应选择哪个通道；
- 前端通道多选界面；
- 任意 PostgreSQL 表或任意 Cypher 的开放式查询；
- 图谱自动从上传文档抽取和增量写入；
- 生产级任务队列、复杂重试退避、缓存或查询审计系统；
- 真实医疗知识数据、诊疗建议或临床决策能力。

## 9. 验收与测试

最小必要测试覆盖：

1. 通道字段默认值、合法值和重复值校验；
2. SQL/Cypher 只读校验与 LIMIT 限制；
3. 图谱和 SQL 通道在首次异常后重试一次；
4. 多通道使用 `asyncio.gather()` 并在一个通道失败时保留其他通道证据；
5. 单通道与多通道回答选择正确提示词；
6. 初始化脚本可在模拟驱动/连接上验证创建语句和演示数据写入意图。

不运行真实 LLM、Neo4j 或 PostgreSQL 的全链路测试；真实服务验收由用户在 Conda `yyy-rag` 环境和 Docker 基础设施启动后执行。

## 10. 设计自检

- 复用现有文档检索、LLM、数据库 Session 和 SSE 路由，不重构无关模块；
- `asyncio.gather()` 只用于请求范围内已选通道，避免全部通道无条件运行；
- GraphRAG 与 NL2SQL 都有限制明确的只读查询与一次重试；
- 演示图谱数据独立存放并标记用途，避免混入生产业务数据；
- 所有项目路径使用相对路径，不记录用户电脑绝对路径。
