# 统一智能问答与通道解耦设计

## 文档状态

- 状态：待用户审核
- 设计日期：2026-09-15
- 设计范围：统一聊天页面、文档通道按需绑定知识库、GraphRAG/NL2SQL 独立问答
- Git 约束：不执行 Git 提交，提交权由用户决定

## 1. 背景与问题

当前系统已新增 `document`、`graph`、`sql` 三个后端检索通道，并支持多通道并行融合。但前端的聊天入口仍放在知识库工作区中，所有聊天都隐式依赖某个知识库；后端 `knowledge_base_id` 也仍然是必填字段并在所有通道执行前校验。

该结构不符合通道语义：GraphRAG 查询 Neo4j 演示图谱，NL2SQL 查询 PostgreSQL 运营演示表，二者不属于任何文档知识库。继续为三个通道分别创建聊天页面会重复流式消息、错误处理和检索设置代码，也会破坏多通道融合的使用方式。

## 2. 目标

1. 取消知识库管理页面中的聊天入口，知识库页面只管理知识库和文档。
2. 新增与知识库管理并列的“智能问答”顶层视图，作为唯一聊天页面。
3. 在统一聊天页面中选择 `document`、`graph`、`sql` 一个或多个通道。
4. 仅当用户选择 `document` 时要求选择知识库；纯 `graph`、纯 `sql` 或 `graph + sql` 时不要求知识库。
5. 保留现有流式 SSE 输出、聊天消息布局、角色设置、检索参数和来源正文规则。
6. 保持旧的文档通道请求与已有 API 路径兼容。

## 3. 非目标

- 不新增三个独立聊天组件或独立 HTTP 路由。
- 不引入 React Router、全局状态库或组件库。
- 不实现后端自动通道路由或根据问题猜测通道。
- 不修改 GraphRAG、NL2SQL、融合检索和初始化脚本的内部算法。
- 不改变非流式 `/api/v1/chat` 和流式 `/api/v1/chat/stream` 的路径。
- 不执行真实 PostgreSQL、Neo4j、Milvus 或 LLM 查询来验证本次页面结构调整。

## 4. 后端 API 契约调整

### 4.1 ChatRequest

```python
class ChatRequest(BaseModel):
    knowledge_base_id: UUID | None = None
    channels: list[Literal["document", "graph", "sql"]] = ["document"]
```

校验规则：

```text
channels 包含 document：
  knowledge_base_id 必填

channels 不包含 document：
  knowledge_base_id 可省略
```

`channels` 仍须非空、最多三个、不可重复。已有客户端没有传 `channels` 时，默认值仍为 `['document']`；因此旧客户端仍必须传 `knowledge_base_id`，行为不变。

### 4.2 服务层

`answer_question()` 和 `stream_answer()` 改为按所选通道决定知识库校验：

1. 包含 `document`：校验 `knowledge_base_id` 非空且对应知识库存在；将其传给文档检索通道。
2. 不包含 `document`：不查询 `KnowledgeBase`，将 `knowledge_base_id=None` 传给通道编排。
3. `collect_evidence()`、`retrieve_document_evidence()` 的知识库参数改为可空；文档通道收到空值时抛出清晰业务异常，防止服务层误用。
4. GraphRAG、NL2SQL 和多通道 `graph + sql` 不读取或校验知识库。

### 4.3 响应兼容性

- 非流式接口仍返回 `ChatResponse`；仅含 graph/sql 的请求返回空 `sources`。
- 流式接口继续发送现有 SSE 文本事件。
- 纯 graph/sql 回答无需文档来源；包含 document 的回答保持模型正文中的 `【来源：文档名称】` 规则。

## 5. 前端信息架构

顶层改为两个 SPA 视图：

```text
知识库管理
  ├── 知识库列表、新建、编辑、删除
  └── 文档上传、导入状态、删除

智能问答
  ├── 通道选择
  ├── 知识库选择（仅 document 已选时）
  ├── 流式聊天消息
  └── 高级检索设置
```

不引入浏览器路由。`App.tsx` 使用一个页面级状态维护当前视图：`workspace` 或 `chat`。

### 5.1 顶层导航

在现有头部的产品名称旁增加两个页面切换按钮：

- `知识库管理`；
- `智能问答`。

当前页面使用诊疗青色下划线和较高对比度显示，按钮保持文字型导航，不添加图标或动画。

### 5.2 统一聊天页面

统一聊天页面是唯一的 `ChatPage`，不再接收固定知识库对象，而是自行获取知识库列表和维护选择状态。

通道选择位于问题输入区域之前，使用三个复选框：

| 通道 | 页面名称 | 默认值 | 说明 |
|---|---|---:|---|
| `document` | 文档知识库 | 选中 | 按所选知识库检索上传文档 |
| `graph` | 医学知识图谱 | 未选中 | 查询 Neo4j 演示图谱 |
| `sql` | 运营数据库 | 未选中 | 查询 PostgreSQL 演示运营表 |

用户至少选择一个通道。全部取消时显示“至少选择一个检索通道”，发送按钮禁用。

当 `document` 被选中时显示知识库下拉框：

- 默认不预选，必须由用户明确选择；
- 还没有知识库时显示“暂无知识库，请先在知识库管理中创建”；
- 未选择知识库时，发送按钮禁用，并显示“文档知识库通道需要选择知识库”。

当用户取消 `document` 时，隐藏知识库选择框，并使 graph/sql 请求不携带 `knowledge_base_id`。

### 5.3 流式消息

保留现有用户消息、助手消息和流式文本追加逻辑。每次发送时，以当前通道、可选知识库 ID、角色、检索数量、重排数量、HyDE 开关构造 `ChatRequest`。用户在流式生成中不能修改通道、知识库、问题或检索设置，防止一个会话请求出现中途参数改变。

## 6. 前端模块边界

```text
app/src/
├── App.tsx                         # workspace/chat 顶层切换和页面编排
├── api/
│   ├── types.ts                    # RetrievalChannel、可选 knowledge_base_id
│   ├── chat.ts                     # 保持 SSE 请求实现，接收更新后的 ChatRequest
│   └── knowledgeBases.ts            # 复用现有知识库列表请求
├── components/
│   ├── AppShell.tsx                # 顶部导航和健康状态
│   ├── ChatPage.tsx                # 唯一聊天页、通道选择、知识库选择、流式消息
│   └── ChatEntryPanel.tsx          # 删除，不再在知识库工作区提供聊天入口
└── test/
    ├── chat-page.test.tsx          # 通道/知识库交互与流式请求参数
    └── app-workspace.test.tsx      # 页面切换和知识库管理无聊天入口
```

为避免组件职责膨胀，`ChatPage` 只管理聊天设置和聊天消息；知识库列表仍由 TanStack Query 的 `listKnowledgeBases()` 管理，不在页面中复制 HTTP 请求。

## 7. 视觉设计

沿用已有深海蓝、病历白和诊疗青的视觉令牌，不重做整体风格。

```text
┌───────────────── 顶部：YYY-RAG / 知识库管理 / 智能问答 / 健康状态 ─────────────────┐
├───────────────────────────────────────────────────────────────────────┤
│ 智能问答                                                               │
│ [x] 文档知识库  [ ] 医学知识图谱  [ ] 运营数据库                        │
│ 知识库： [请选择知识库 ▼]（仅文档通道已选时）                            │
│                                                                         │
│ 聊天消息区                                                              │
│                                                                         │
│ 问题输入框 / 高级检索设置 / 发送                                        │
└───────────────────────────────────────────────────────────────────────┘
```

通道选择为带说明的横向复选项；小屏幕下折为单列。它是控制检索来源的核心信息，使用边框与选中背景表达状态，不以装饰卡片堆叠。

## 8. 错误和空状态

- 通道未选择：页面级提示，发送禁用；
- document 已选但无知识库：显示引导到知识库管理；
- document 已选但未选知识库：发送禁用；
- 后端 422：展示后端校验详情；
- graph/sql 服务不可用：由后端多通道策略容忍单通道失败；若全部无证据则展示后端返回的统一文案；
- 知识库列表加载中：选择器显示“正在加载知识库”。

## 9. 测试与验收

### 后端最小测试

1. document 通道缺失知识库 ID 时返回验证错误；
2. graph/sql-only 请求允许没有知识库 ID；
3. 服务层在 graph/sql-only 时不访问 `KnowledgeBase`；
4. 文档通道仍按知识库 ID 检索。

### 前端最小测试

1. 页面导航切换到统一智能问答，知识库管理区域不再出现聊天入口；
2. 默认发送 `channels: ['document']`，且未选知识库时不可发送；
3. 选中 graph/sql 并取消 document 后隐藏知识库选择器，流式请求不含 `knowledge_base_id`；
4. 选中 document + graph 时显示知识库选择器，并向流式请求发送两个通道和已选知识库 ID；
5. 保留现有流式文本拼接测试。

### 非真实验收

不运行真实模型、PostgreSQL、Neo4j、Milvus 或初始化脚本；只通过模拟 API 和单元测试验证请求契约与页面状态。

## 10. 设计自检

- 一个聊天组件服务三种通道和融合模式，避免重复聊天实现；
- 文档知识库仅在 document 通道被选择时出现，GraphRAG/NL2SQL 不再被错误绑定；
- 后端与前端在 `knowledge_base_id` 条件必填语义上一致；
- 保持旧接口路径与默认 document 行为兼容；
- 仅修改与统一聊天、条件知识库校验相关的文件；
- 文档只使用项目相对路径，未记录用户电脑绝对路径。
