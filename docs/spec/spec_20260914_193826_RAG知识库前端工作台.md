## 1. 背景与范围

当前仓库已有用于文档知识库的 FastAPI 后端，覆盖知识库 CRUD、文档上传与异步导入、文档详情和删除、RAG 问答、依赖健康检查。项目根目录下的 `frontend/` 为空，本次按用户要求在项目根目录新建独立前端目录 `app/`，不修改现有 Python 后端业务逻辑。

本次交付一个单页知识库工作台，面向医疗文档 RAG 的日常使用：用户先创建或选择知识库，再上传并等待文档导入，最后在同一知识库范围内发起问答并查看来源片段。

### 1.1 本次实现

1. 知识库的创建、分页列表、编辑、删除和当前选择。
2. 已选知识库下的文档分页列表、单文件上传、异步导入状态跟踪、删除。
3. 已选知识库范围内的 RAG 问答、检索参数设置、回答与来源片段展示。
4. 后端健康状态展示和接口错误提示。
5. 开发环境 API 代理，避免本地开发时依赖后端 CORS 配置。
6. 与核心请求、轮询和交互对应的最小自动化测试。

### 1.2 明确不实现

- 用户登录、权限、角色管理、多租户；
- 文档在线预览、下载、编辑、重试导入、进度百分比；
- 多轮会话保存、服务端聊天历史、流式回答；
- 后端接口、数据库模型或 CORS 行为修改；
- 引入组件库、全局状态库或额外的后端 BFF 层。

## 2. 运行前提

当前环境未检测到 `node` 和 `npm` 命令。实际实现和验证前需要安装可运行所选 Vite 版本的 Node.js LTS，并确认 `node --version` 与 `npm --version` 可用；此项是环境前置条件，不通过修改仓库代码规避。

后端仍由现有启动方式提供服务。开发时前端开发服务器将 `/api` 请求代理至该服务；部署时应通过同域反向代理转发 `/api`，因此本次不为纯前端联调新增跨域配置。

## 3. 技术方案

### 3.1 技术栈

- React：界面组件与交互状态；
- TypeScript：接口数据、组件参数、请求错误的静态约束；
- Vite：本地开发、构建与 API 代理；
- TanStack Query：服务端状态缓存、失效刷新、异步请求状态；
- 原生 CSS：集中维护视觉令牌和响应式布局，不引入通用组件库；
- Vitest + React Testing Library：覆盖 API 适配层和关键交互。

TanStack Query 仅管理后端数据，不增加 Redux、Zustand 等第二套状态机制。当前选中知识库、弹窗开关、输入框内容等短生命周期界面状态保留在对应 React 组件中。

## 4. 视觉与界面设计

### 4.1 产品定位

这是医疗文档知识库的操作台，不是营销首页。目标用户需要在有限时间内判断：当前操作的是哪个知识库、哪些文档可以用于问答、回答依据来自哪里。因此界面采用“临床档案夹 + 对话工作台”结构：信息层级清晰、克制、优先可读性，避免大面积装饰卡片和无意义动画。

### 4.2 设计令牌

| 名称 | 色值 | 用途 |
|---|---:|---|
| 深海蓝 | `#123047` | 侧栏、主标题、主要文字 |
| 病历白 | `#F7FAFC` | 页面背景和大面积留白 |
| 雾灰 | `#E3EDF1` | 分隔线、禁用状态、次级区域 |
| 诊疗青 | `#147C7B` | 主操作、选中态、健康正常 |
| 琥珀黄 | `#D08A2E` | 导入中与需要注意的状态 |
| 朱砂红 | `#B63D3D` | 失败、不可逆删除确认 |

字体优先采用系统中可用的中文无衬线字体，正文使用常规字重，标题仅以字号和深海蓝建立层级。界面不依赖外部字体下载，避免运行环境与网络影响可读性。

### 4.3 布局

桌面端以三段式信息架构呈现：左侧是知识库导航，右侧主区域的上方显示当前知识库摘要，下方将文档管理和问答并列。两者服务同一个当前选中的知识库，避免用户在不同页面之间切换时失去上下文。

```text
┌──────────────────── 顶部状态栏：产品名 / API 健康状态 ────────────────────┐
├───────────────┬──────────────────────────────────────────────────────────┤
│ 知识库        │ 当前知识库名称、描述、编辑和删除                           │
│ + 新建         ├────────────────────────┬─────────────────────────────────┤
│ 列表与数量     │ 文档                    │ 基于此知识库提问                │
│                │ 上传区、分页表格、状态   │ 问题、检索设置、回答、来源       │
└───────────────┴────────────────────────┴─────────────────────────────────┘
```

- 宽度不小于 1100px：左侧固定约 280px，文档区和问答区并列；
- 768px 至 1099px：左侧缩窄，文档区与问答区上下排列；
- 小于 768px：侧栏改为顶部横向选择区，主内容单列，所有按钮保留文字标签；
- 键盘焦点使用明确的青色描边；遵循用户系统的减少动态效果偏好，不设置非必要入场动画。

### 4.4 关键交互

1. **空状态**：没有知识库时，主区域只展示“创建第一个知识库”说明和新建按钮；未选择知识库时，文档和问答操作禁用并说明原因。
2. **创建与编辑**：名称必填，描述可选。提交时按钮展示进行中状态；成功后刷新列表并选中新创建或更新后的知识库。
3. **删除知识库**：必须二次确认。后端返回 409 时提示“知识库仍含文档，请先删除文档”，不从界面列表移除。
4. **上传文档**：仅允许 `.pdf`、`.docx`、`.txt`、`.md`，提供可选分类，单次提交一个文件以匹配后端单文件接口。后端仍是最终校验方。
5. **导入状态**：上传拿到 202 后立即刷新文档列表，并开始每 2 秒请求该文档详情。`pending` 和 `processing` 显示导入中；`completed` 显示分块数；`failed` 显示后端返回的失败原因。组件卸载或任务结束时停止轮询。
6. **删除文档**：仅在确认后请求删除。返回 409 时提示文档正在导入，不能删除；成功后刷新当前知识库文档列表。
7. **问答**：问题为空时不提交。默认发送后端默认参数：`role=patient`、`top_k=20`、`rerank_top_k=5`、`use_hyde=true`。高级设置可展开修改这些字段，并在前端保持 `rerank_top_k <= top_k`；服务端校验仍为最终依据。
8. **来源**：回答下方按相关度展示文档名、页码、分块序号、分数和文本片段。没有来源时显示明确空状态。

## 5. 后端接口映射

所有浏览器请求使用 `VITE_API_BASE_URL`（默认空字符串）作为前缀；API 路径仍保留 `/api/v1`。开发服务器通过 `VITE_DEV_API_TARGET`（默认 `http://127.0.0.1:8080`）代理 `/api`，不重写路径。

| 前端动作 | 方法和路径 | 请求内容 | 使用结果 |
|---|---|---|---|
| 获取服务状态 | `GET /api/v1/health` | 无 | 顶部健康标记 |
| 列出知识库 | `GET /api/v1/knowledge-bases?skip&limit` | 分页参数 | 侧栏列表和总数 |
| 创建知识库 | `POST /api/v1/knowledge-bases` | `{ name, description }` | 新增并选中 |
| 更新知识库 | `PUT /api/v1/knowledge-bases/{id}` | `{ name, description }` | 刷新当前摘要与列表 |
| 删除知识库 | `DELETE /api/v1/knowledge-bases/{id}` | 无 | 成功后清空选择并刷新列表 |
| 列出文档 | `GET /api/v1/knowledge-bases/{id}/documents?skip&limit` | 分页参数 | 文档表格 |
| 上传文档 | `POST /api/v1/knowledge-bases/{id}/documents` | `multipart/form-data` 的 `file`、`category` | 启动状态跟踪 |
| 查询导入状态 | `GET /api/v1/documents/{id}` | 无 | 轮询任务状态和错误详情 |
| 删除文档 | `DELETE /api/v1/documents/{id}` | 无 | 刷新文档表格 |
| RAG 问答 | `POST /api/v1/chat` | `ChatRequest` | 展示 `answer` 与 `sources` |

前端类型严格对应现有 Pydantic 响应字段：知识库含 `id`、`name`、`description`、`created_at`、`updated_at`；文档含导入状态、分块数和任务字段；聊天来源含文档信息、页码、分块序号、分数和文本。日期字段按浏览器本地时区格式化，原始 ISO 字符串不改写后端数据。

## 6. 数据流与错误处理

### 6.1 Query 缓存键

```text
['health']
['knowledge-bases', { skip, limit }]
['documents', knowledgeBaseId, { skip, limit }]
['document', documentId]
```

创建、更新、删除知识库后失效 `knowledge-bases`；上传和删除文档后失效当前 `documents`；轮询终态后再次失效当前 `documents`。问答不做缓存，避免将旧回答误认为当前知识库的实时结果。

### 6.2 HTTP 统一处理

`request<T>` 负责：

1. 以 `fetch` 发送请求，普通 JSON 请求设置 `Content-Type: application/json`；`FormData` 上传不手动设置该请求头；
2. `204 No Content` 返回 `undefined`；其余成功响应解析 JSON；
3. 非成功响应优先读取 JSON 的 `detail` 字段，构造包含 HTTP 状态码和展示文案的 `ApiError`；响应不是 JSON 或网络不可达时提供通用中文错误文案；
4. UI 只显示操作相关的错误，不暴露请求体、服务器堆栈、密钥或连接配置。

### 6.3 已知状态码的用户反馈

- 404：资源已不存在，刷新相应列表；
- 409：保留当前界面数据，说明操作条件不满足；
- 422：在表单或上传区域显示后端校验信息；
- 500：显示“服务处理失败，请稍后重试”；
- 503：顶部标记为不可用，保留工作区数据，不阻止用户查看已加载内容；
- 网络错误：显示“无法连接后端服务”，不把错误对象直接渲染到页面。

## 8. 验收标准

1. 所有前端源代码只位于 `app/`，不覆盖仓库现有 `frontend/` 空目录，也不修改后端业务代码。
2. 用户可以通过 UI 完成现有后端暴露的全部第一版业务操作。
3. 上传请求与当前后端单文件 `multipart/form-data` 契约一致，并能展示异步导入结果。
4. 问答始终携带当前选中知识库 ID，并展示后端返回的来源片段。
5. 开发环境中 `/api` 请求由 Vite 代理到后端，不依赖 CORS。
6. 请求、轮询、错误解析和 UI 职责分离，后续增加接口时无需在多个组件复制 HTTP 代码。
7. 通过前端测试和生产构建；不执行 Git 提交。

## 9. 设计自检

- **范围**：设计只覆盖当前后端已提供的接口，没有添加认证、流式聊天、文档预览等后端未支持能力。
- **一致性**：异步导入采用后端实际支持的文档详情接口轮询；知识库删除的 409 约束在 UI 中明确说明；聊天参数遵循当前请求模型的默认值和大小关系。
- **可维护性**：HTTP 请求集中于 API 层，服务端缓存集中于 TanStack Query，轮询独立为 Hook，页面组件不直接操作网络。
- **风险**：当前系统没有可用 Node.js/npm；在环境准备完成前不能执行依赖安装、测试或构建。这不是前端代码问题，需要先满足运行前提。
- **路径合规**：文档只使用项目内相对路径，不包含用户电脑的绝对路径。
