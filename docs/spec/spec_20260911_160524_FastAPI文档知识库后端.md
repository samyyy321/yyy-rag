## 1. 背景与当前仓库事实

当前仓库已经具备基础 RAG 能力：

- `src/index/doc_ingestion.py` 负责文档解析、切块、Embedding 和 Milvus 写入；
- `src/query/doc_rag.py` 负责 Milvus 检索、Reranker、HyDE 和回答生成；
- `src/infra/milvus_client.py` 负责创建 Milvus 客户端；
- `src/core/config.py` 负责环境变量读取；
- `src/evaluation/` 和 `RAG-assessment/` 是独立 TruLens 评测链路。

当前仓库尚未提供 FastAPI、PostgreSQL 业务模型、Alembic 迁移、MinIO 业务客户端和 API 路由。因此本需求属于新增后端子系统，不是对现有 API 的小范围修补。实现时只改造现有索引和查询函数的必要接口，不重构无关的评测或 RAG 模块。

## 2. 目标

1. 使用 PostgreSQL `rag` 数据库保存知识库、文档元数据和导入任务。
2. 使用 MinIO `rag-documents` bucket 保存上传的原始文件。
3. 使用新的 Milvus `knowledge_docs_v2` collection 保存文档分块向量。
4. 所有业务 ID 使用 Python 生成的 UUID4，并在 PostgreSQL、MinIO、Milvus 和 API 之间保持一致。
5. 提供知识库 CRUD、文档上传/查询/删除、RAG 问答和健康检查接口。
6. 通过业务代码维护表间关联，不创建任何数据库级外键。
7. 通过数据库事务和 PostgreSQL 行锁处理知识库删除、文档创建、导入任务认领和文档删除之间的并发关系。
8. 通过 PostgreSQL/Alembic 生成表及字段的中文数据库注释，使 `\d+` 可以查看完整说明。

## 3. 非目标

本版本不实现：

- 用户认证、权限、租户隔离和管理员角色；
- Redis、Celery 或其他独立任务队列；
- 文档在线编辑、版本管理和重复文件去重；
- 知识库软删除；
- 数据库级 `FOREIGN KEY`、级联删除和数据库触发器；
- 旧 `knowledge_docs` collection 的自动数据迁移、自动删除或无归属数据猜测迁移；
- TruLens 评测与生产 API 的合并；
- 与本需求无关的现有 RAG 代码重构。

## 5. 标识、关联和状态不变量

### 5.1 ID 规则

- `knowledge_bases.id`、`documents.id`、`ingestion_tasks.id` 均为 UUID4；
- ID 在业务层使用 `uuid.uuid4()` 生成，不使用文档名 MD5、数据库自增 ID 或 Milvus `auto_id`；
- `documents.id` 的字符串形式同时用于：
  - PostgreSQL `documents.id`；
  - MinIO 对象键的目录部分；
  - Milvus `doc_id`；
  - API 返回的 `document_id`；
- Milvus 分块主键固定为 `f"{document_id}_{chunk_index}"`；
- API 可以接收 UUID 字符串，但在进入服务层前转换为 `uuid.UUID`，无效格式由 FastAPI 返回 422。

### 5.2 业务关联规则

以下列只保存业务 ID，不创建外键：

```text
documents.knowledge_base_id
ingestion_tasks.document_id
```

业务层必须保证：

1. 创建文档前锁定并检查知识库存在；
2. 知识库下的文档列表使用 `knowledge_base_id` 条件查询；
3. 任何带知识库上下文的文档操作同时匹配 `document_id` 和 `knowledge_base_id`；
4. 创建导入任务前检查文档存在；
5. 删除知识库前在同一事务内检查文档数量；
6. 不允许导入 worker 在文档删除流程之后继续写入 Milvus；
7. 删除文档前同时清理 Milvus 和 MinIO，数据库记录只在外部清理成功后删除。

### 5.3 文档和任务状态

文档 `status` 使用以下值：

```text
pending     已创建元数据，等待后台任务认领
processing   后台任务已认领，正在解析或写入向量
completed   导入成功
failed      导入失败，error_message 保存原因
```

任务 `status` 使用以下值：

```text
pending     等待执行
processing  已开始执行
completed   执行成功
failed      执行失败
```

允许的核心转换：

```text
Document: pending -> processing -> completed
Document: pending -> processing -> failed
Task:     pending -> processing -> completed
Task:     pending -> processing -> failed
```

`pending` 和 `processing` 文档均不可删除。只有 `completed` 和 `failed` 文档进入删除流程。

## 6. PostgreSQL 设计

### 6.1 连接

生产业务连接只使用：

```env
DATABASE_URL=postgresql+psycopg://rag:rag@localhost:5432/rag
```

不得把 `TRULENS_DATABASE_URL` 作为生产数据库的回退值。数据库引擎使用 SQLAlchemy 2.x，驱动使用 psycopg 3，Session 使用每个请求/任务独立的 `Session`。

### 6.2 通用数据库规则

- 使用 PostgreSQL `UUID`、`VARCHAR`、`TEXT`、`BIGINT`、`INTEGER` 和无时区 `TIMESTAMP`；
- 应用以 UTC 生成时间，并以无时区 UTC 时间写入 `TIMESTAMP`；
- 三张表均不声明 SQLAlchemy `ForeignKey`，也不声明依赖数据库外键的 `relationship`；
- `id` 由应用生成 UUID4；
- `created_at`、`updated_at` 由应用在创建/更新时维护；
- `documents.knowledge_base_id`、`ingestion_tasks.document_id` 建立普通索引，不建立外键；
- Alembic migration 必须显式执行 `COMMENT ON TABLE` 和每个字段的 `COMMENT ON COLUMN`。

### 6.3 `knowledge_bases`

表注释：`知识库主表`。

| 字段 | PostgreSQL 类型 | 约束 | 中文注释 |
|---|---|---|---|
| `id` | UUID | PRIMARY KEY | 知识库唯一标识，UUID4 |
| `name` | VARCHAR(100) | NOT NULL | 知识库名称 |
| `description` | TEXT | NULL | 知识库描述 |
| `created_at` | TIMESTAMP | NOT NULL | 创建时间，UTC |
| `updated_at` | TIMESTAMP | NOT NULL | 最后更新时间，UTC |

### 6.4 `documents`

表注释：`文档主表，保存原始文件和导入状态`。

| 字段 | PostgreSQL 类型 | 约束 | 中文注释 |
|---|---|---|---|
| `id` | UUID | PRIMARY KEY | 文档唯一标识，UUID4 |
| `knowledge_base_id` | UUID | NOT NULL、普通索引 | 所属知识库唯一标识，由业务代码维护关联 |
| `original_name` | VARCHAR(255) | NOT NULL | 上传时的原始文件名 |
| `object_key` | VARCHAR(500) | NOT NULL | MinIO 中的原始文件对象键 |
| `content_type` | VARCHAR(100) | NULL | 文件 MIME 类型 |
| `file_size` | BIGINT | NOT NULL | 文件大小，单位为字节 |
| `doc_type` | VARCHAR(50) | NOT NULL | 文档类型，例如 pdf、docx、txt、md |
| `category` | VARCHAR(100) | NOT NULL | 文档分类 |
| `status` | VARCHAR(30) | NOT NULL | 文档导入状态 |
| `chunk_count` | INTEGER | NOT NULL DEFAULT 0 | 已写入 Milvus 的分块数量 |
| `error_message` | TEXT | NULL | 最近一次导入失败信息 |
| `created_at` | TIMESTAMP | NOT NULL | 创建时间，UTC |
| `updated_at` | TIMESTAMP | NOT NULL | 最后更新时间，UTC |

### 6.5 `ingestion_tasks`

表注释：`文档导入任务表`。

| 字段 | PostgreSQL 类型 | 约束 | 中文注释 |
|---|---|---|---|
| `id` | UUID | PRIMARY KEY | 导入任务唯一标识，UUID4 |
| `document_id` | UUID | NOT NULL、普通索引 | 被导入的文档唯一标识，由业务代码维护关联 |
| `status` | VARCHAR(30) | NOT NULL | 导入任务状态 |
| `error_message` | TEXT | NULL | 导入失败信息 |
| `started_at` | TIMESTAMP | NULL | 任务开始执行时间，UTC |
| `finished_at` | TIMESTAMP | NULL | 任务结束时间，UTC |
| `created_at` | TIMESTAMP | NOT NULL | 任务创建时间，UTC |
| `updated_at` | TIMESTAMP | NOT NULL | 任务最后更新时间，UTC |

不增加数据库外键，不使用 `ON DELETE CASCADE`。任务删除由文档删除服务在同一数据库事务中显式执行。

## 7. 并发和事务协议

### 7.1 知识库删除与文档创建

创建文档和删除知识库必须争用同一条知识库行锁：

```text
创建文档：BEGIN
  SELECT knowledge_bases WHERE id = :knowledge_base_id FOR UPDATE
  不存在 -> 404
  存在 -> INSERT documents 和 ingestion_tasks
COMMIT

删除知识库：BEGIN
  SELECT knowledge_bases WHERE id = :knowledge_base_id FOR UPDATE
  不存在 -> 404
  SELECT COUNT(*) FROM documents WHERE knowledge_base_id = :knowledge_base_id
  count > 0 -> ROLLBACK + 409
  count = 0 -> DELETE knowledge_bases + COMMIT
```

因此，已获得知识库锁的文档创建会先完成或回滚，知识库删除随后重新检查文档数量，不会绕过并发创建。

### 7.2 导入任务认领与文档删除

后台 worker 必须使用独立 Session 执行以下步骤：

```text
BEGIN
  SELECT ingestion_tasks WHERE id = :task_id FOR UPDATE
  SELECT documents WHERE id = task.document_id FOR UPDATE
  task/doc 不存在或 task 非 pending -> 结束
  将 task.status 和 document.status 更新为 processing
COMMIT
```

worker 只有在成功提交 `processing` 状态后才允许从 MinIO 下载、调用解析、Embedding 和 Milvus 写入。删除文档同样先锁定文档行：

```text
BEGIN
  SELECT documents WHERE id = :document_id FOR UPDATE
  pending/processing -> ROLLBACK + 409
  completed/failed -> 保持行锁，执行外部清理
```

这样删除请求和 worker 不会同时认为自己可以处理同一个文档。worker 完成或失败时更新前再次锁定文档，并且只有文档仍为 `processing` 时才写入最终状态。

### 7.3 外部存储与数据库的一致性边界

PostgreSQL 事务不能覆盖 MinIO 和 Milvus。实现采用以下顺序：

- 上传：先写 MinIO，成功后在 PostgreSQL 事务中写入文档和任务；数据库写入失败时尝试删除刚上传的对象；
- 导入：先把文档标记为 `processing`，成功写入 Milvus 后在事务中写入 `completed` 和 `chunk_count`；异常时写入 `failed`；
- 删除：保持文档行锁，先删除 Milvus 分块，再删除 MinIO 对象，两个外部操作均成功后删除任务、文档和数据库记录；任一外部操作失败则回滚数据库记录并返回 500，保留记录以便重试；
- Milvus/MinIO 的删除操作应允许“对象不存在”作为幂等成功，避免部分清理后的重试无法完成。

## 8. MinIO 设计

使用现有 Docker Compose 中的 MinIO 和 bucket：

```env
MINIO_ENDPOINT=localhost:9000
MINIO_ACCESS_KEY=minioadmin
MINIO_SECRET_KEY=minioadmin
MINIO_BUCKET=rag-documents
MINIO_SECURE=false
```

FastAPI 在宿主机运行时使用 `localhost:9000`，在同一 Compose 网络内运行时使用 `minio:9000`。对象键为：

```text
{document_id}/{safe_original_filename}
```

`original_name` 保留客户端原始文件名；对象键中的文件名只取 basename 并规范化路径分隔符，避免客户端传入 `../` 或目录分隔符改变对象层级。该处理不改变 API 返回的原始文件名。

`src/infra/minio_client.py` 提供最小封装：上传文件流、下载到临时路径、删除对象、检查 bucket。MinIO SDK 是同步 I/O，异步路由和后台任务通过 `asyncio.to_thread` 或同步后台 worker 调用，不直接阻塞异步事件循环。

## 9. Milvus 设计

### 9.1 生产 Collection

生产 API 和新导入流程统一使用：

```text
knowledge_docs_v2
```

不修改、不删除旧的 `knowledge_docs`。新 collection schema：

```text
id                  VARCHAR PRIMARY KEY
knowledge_base_id   VARCHAR

doc_id              VARCHAR
doc_name            VARCHAR
doc_type            VARCHAR
category            VARCHAR
page_number         INT64
chunk_index         INT64
text                VARCHAR
embedding           FLOAT_VECTOR
```

`knowledge_base_id`、`doc_id` 的 `max_length` 至少为 64，`id` 的 `max_length` 至少为 128，具体值与现有 Milvus SDK 可接受范围保持一致。向量维度使用现有 `MILVUS_DIM` 配置，默认 1024；度量使用 COSINE，索引继续使用 IVF_FLAT。

### 9.2 写入

`src/index/doc_ingestion.py` 的 `ingest_file` 不再根据文件名计算 ID，改为显式接收：

```python
async def ingest_file(
    file_path: str,
    document_id: str,
    knowledge_base_id: str,
    doc_name: str,
    doc_type: str,
    category: str,
    embedding_model: Embeddings,
    milvus_client: MilvusClient,
) -> int:
    ...
```

每个分块必须写入：

```python
{
    "id": f"{document_id}_{chunk_index}",
    "knowledge_base_id": knowledge_base_id,
    "doc_id": document_id,
    "doc_name": doc_name,
    "doc_type": doc_type,
    "category": category,
    "page_number": page_number,
    "chunk_index": chunk_index,
    "text": text,
    "embedding": embedding,
}
```

导入前只按 `knowledge_base_id + doc_id` 删除同一文档已有分块，不能按文件名或仅按 `doc_id` 跨知识库删除。

### 9.3 检索和删除

API RAG 查询必须使用知识库过滤：

```text
knowledge_base_id == "{knowledge_base_id}"
```

如果同时按文档类型过滤，组合为：

```text
knowledge_base_id == "{knowledge_base_id}" && doc_type == "{doc_type}"
```

检索输出字段至少包含 `knowledge_base_id`、`doc_id`、`doc_name`、`doc_type`、`category`、`page_number`、`chunk_index`、`text`。文档删除使用双重过滤：

```text
knowledge_base_id == "{knowledge_base_id}" && doc_id == "{document_id}"
```

旧 `knowledge_docs` 不允许被 API 读取或写入。已有旧数据没有可靠的知识库归属，不自动搬迁；业务方需把原始文件重新上传到目标知识库。

## 10. API 合约

统一前缀：`/api/v1`。

### 10.1 知识库接口

```text
POST   /api/v1/knowledge-bases
GET    /api/v1/knowledge-bases
GET    /api/v1/knowledge-bases/{knowledge_base_id}
PUT    /api/v1/knowledge-bases/{knowledge_base_id}
DELETE /api/v1/knowledge-bases/{knowledge_base_id}
```

创建请求：

```json
{
  "name": "医学知识库",
  "description": "医学文档"
}
```

`name` 必填且长度 1-100；`description` 可空。PUT 只更新 `name` 和 `description`。列表返回 `items`、`total`、`skip`、`limit`，按 `created_at DESC` 排序。详情或更新/删除的知识库不存在返回 404。删除时存在任意文档返回 409，否则删除知识库记录并返回 204。

### 10.2 文档接口

```text
POST   /api/v1/knowledge-bases/{knowledge_base_id}/documents
GET    /api/v1/knowledge-bases/{knowledge_base_id}/documents
GET    /api/v1/documents/{document_id}
DELETE /api/v1/documents/{document_id}
```

上传使用 `multipart/form-data`：

```text
file      必填，文件内容
category  可选，默认 default
```

第一版支持 `.pdf`、`.docx`、`.txt`、`.md`。`doc_type` 由安全的扩展名推导，不接受客户端覆盖。上传成功返回 202：

```json
{
  "document_id": "7f9c6b8e-7b6d-4c5a-9e2d-1c4f87b8a321",
  "task_id": "b8d1f80a-6f9c-45d0-9e0e-9c39ef7ea2d5",
  "status": "pending"
}
```

文档列表必须先确认知识库存在，再按 `knowledge_base_id` 查询；返回分页结果。文档详情返回所有业务字段和最新任务信息；文档不存在返回 404。文档删除只接收 `document_id`，服务层锁定文档并按文档记录中的 `knowledge_base_id` 清理 Milvus。文档状态为 pending/processing 返回 409；completed/failed 才允许删除。

### 10.3 Chat 接口

```text
POST /api/v1/chat
```

请求：

```json
{
  "knowledge_base_id": "7f9c6b8e-7b6d-4c5a-9e2d-1c4f87b8a321",
  "question": "什么是 Transformer？",
  "role": "patient",
  "top_k": 20,
  "rerank_top_k": 5,
  "use_hyde": true
}
```

`knowledge_base_id` 和 `question` 必填，数值参数使用现有默认值并限制为正数，且 `rerank_top_k <= top_k`。服务层先检查知识库存在，再调用带 `knowledge_base_id` 的检索函数。返回：

```json
{
  "answer": "...",
  "sources": [
    {
      "document_id": "...",
      "document_name": "example.pdf",
      "page_number": 3,
      "chunk_index": 2,
      "score": 0.91,
      "text": "..."
    }
  ]
}
```

无已完成文档或无命中结果时，返回现有 RAG 无结果回答，并返回空 `sources`，不跨知识库检索。

### 10.4 健康检查

```text
GET /api/v1/health
```

检查应用、PostgreSQL、MinIO bucket 和 Milvus 的基础连通性；全部正常返回 200 和 `{"status":"ok"}`。任一依赖不可用返回 503 和 `{"status":"unhealthy"}`，不暴露连接字符串、密码或底层异常堆栈。

## 12. 部署和 collection 切换

1. 启动现有 PostgreSQL、MinIO、Milvus Compose 服务；
2. 执行 `alembic upgrade head`，创建 `rag` 数据库中的三张业务表并写入注释；
3. 首次启动 API 或执行初始化命令时创建 `knowledge_docs_v2`；
4. 通过新 API 重新上传已有原始文件，使每个文件获得新的 `knowledge_base_id` 和 UUID4 `document_id`；
5. 验证按知识库检索、文档删除、并发保护和 `\d+` 注释；
6. 验证完成前保留旧 `knowledge_docs`；生产 API 只读取 `knowledge_docs_v2`；
7. 回滚代码时可将 collection 配置切回旧链路，但旧数据不具备新知识库隔离语义，不得把旧 collection 当作新 API 的生产数据源。

本次不提供自动搬迁旧 collection 的脚本，也不自动删除旧 collection。

## 13. 验收标准

### 数据库

- `DATABASE_URL` 指向 PostgreSQL `rag`，业务代码不读取 `TRULENS_DATABASE_URL`；
- 三张表字段、类型、默认值与本设计一致；
- 三张表没有任何 `FOREIGN KEY`；
- `\d+ knowledge_bases`、`\d+ documents`、`\d+ ingestion_tasks` 能看到表注释和每个字段的中文注释；
- 三类业务 ID 均为 UUID4。

### 业务和并发

- 不存在知识库时创建文档返回 404；
- 创建文档与删除知识库并发时，知识库行锁保证删除不会绕过已提交的文档；
- pending/processing 文档不能删除；
- worker 认领任务与删除文档并发时，至少一方因状态/行锁失败，不能出现 worker 在删除后写入 Milvus；
- 知识库有文档时删除返回 409，无文档时删除成功。

### 存储和检索

- MinIO 对象键包含同一个 `document_id`；
- Milvus 生产 collection 为 `knowledge_docs_v2`，每条记录包含 `knowledge_base_id` 和 `doc_id`；
- Chat 检索始终传递 `knowledge_base_id` 过滤条件；
- 文档删除使用 `knowledge_base_id + doc_id` 双重过滤；
- API 不读写旧 `knowledge_docs`。

### API 和验证

- API 路径与本设计完全一致；
- 上传返回 202 并可通过文档详情查询异步状态；
- 主要 404、409、422、500、503 行为符合本设计；
- 通过编译、单元测试、API 集成测试、Alembic 注释检查和 Milvus/MinIO 集成验证；
- 不执行 Git 提交。
