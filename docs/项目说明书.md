# YYY-RAG 项目说明书

- 文档版本：2026-09-14
- 项目类型：文档知识库、RAG 检索问答和 TruLens 评测后端
- 运行环境：Conda `yyy-rag`
- API 框架：FastAPI
- 主要存储：PostgreSQL、MinIO、Milvus
- 可选解析服务：MinerU
- 模型服务：DashScope 兼容 OpenAI 接口

## 1. 项目定位

本项目用于构建一个按知识库隔离的文档 RAG 系统。用户先创建知识库，再上传 PDF、DOCX、TXT 或 Markdown 文档。系统保存原文件，异步完成解析、切块、Embedding 和向量入库，之后可以在指定知识库范围内进行问答，并返回检索来源。

项目同时包含 TruLens 评测能力，用于评估检索上下文相关性、回答相关性和回答事实支撑度。

## 2. 核心能力

### 2.1 生产 API

- 知识库 CRUD 和分页查询。
- 文档上传、文档列表、文档详情和文档删除。
- 文档异步导入任务状态跟踪。
- 指定知识库范围的 RAG Chat。
- PostgreSQL、MinIO 和 Milvus 健康检查。

### 2.2 RAG 导入链路

```text
上传文件
  -> MinIO 保存原文件
  -> PostgreSQL 创建文档和导入任务
  -> BackgroundTasks 认领任务
  -> MinIO 下载临时文件
  -> MinerU 解析，失败时回退 LlamaIndex
  -> 文档切块
  -> DashScope Embedding
  -> Milvus collection 写入
  -> 更新文档和任务状态
```

### 2.3 RAG 查询链路

```text
Chat 请求
  -> PostgreSQL 校验知识库存在
  -> 生成查询向量或执行 HyDE
  -> Milvus 按 knowledge_base_id 检索
  -> DashScope Rerank 重排
  -> 使用上下文和角色提示词调用 LLM
  -> 返回回答和来源片段
```

## 6. 数据模型

### 6.1 `knowledge_bases`

知识库主表，保存知识库名称、描述和时间字段。

### 6.2 `documents`

文档元数据和导入状态表，重要字段包括：

| 字段 | 含义 |
|---|---|
| `id` | 文档 UUID |
| `knowledge_base_id` | 所属知识库 UUID |
| `original_name` | 上传时的原始文件名 |
| `object_key` | MinIO 对象键 |
| `content_type` | MIME 类型 |
| `file_size` | 文件大小，单位为字节 |
| `doc_type` | `pdf`、`docx`、`txt` 或 `md` |
| `category` | 文档分类 |
| `status` | `pending`、`processing`、`completed` 或 `failed` |
| `chunk_count` | 已写入 Milvus 的分块数 |
| `error_message` | 最近一次导入错误 |
| `created_at` | 创建时间，UTC |
| `updated_at` | 更新时间，UTC |

### 6.3 `ingestion_tasks`

异步导入任务表。当前数据库模型不声明 PostgreSQL 外键，`document_id` 和 `knowledge_base_id` 的关联由服务层维护。

| 字段 | 含义和变化 |
|---|---|
| `id` | 任务 UUID，创建后不变 |
| `document_id` | 对应文档 UUID，创建后不变 |
| `status` | `pending -> processing -> completed/failed` |
| `error_message` | 失败时写入错误信息，最多 2000 字符 |
| `started_at` | worker 认领任务时写入 |
| `finished_at` | 成功或失败时写入 |
| `created_at` | 任务创建时间 |
| `updated_at` | 每次状态变化时更新 |

## 7. 文档上传和导入状态

### 7.1 上传阶段

调用：

```text
POST /api/v1/knowledge-bases/{knowledge_base_id}/documents
```

服务层按以下顺序执行：

1. 校验文件扩展名。
2. 将上传内容读入内存。
3. 生成 `document_id` 和 `task_id`。
4. 将原文件上传到 MinIO。
5. 使用行锁确认知识库存在。
6. 在同一个 PostgreSQL 事务中创建 `documents` 和 `ingestion_tasks`。
7. 提交事务。
8. 注册 FastAPI `BackgroundTasks`。
9. 返回 `202 Accepted`。

初始数据状态：

```text
documents.status            = pending
documents.chunk_count       = 0
documents.error_message     = NULL
ingestion_tasks.status      = pending
ingestion_tasks.started_at  = NULL
ingestion_tasks.finished_at = NULL
ingestion_tasks.error_message = NULL
```

### 7.2 worker 认领任务

`run_ingestion_task` 首先通过 `SELECT ... FOR UPDATE` 锁定任务和文档，只有当两者都是 `pending` 时才继续执行。

更新为：

```text
documents.status       = processing
documents.error_message = NULL

ingestion_tasks.status       = processing
ingestion_tasks.started_at   = 当前 UTC 时间
ingestion_tasks.updated_at   = 当前 UTC 时间
ingestion_tasks.finished_at  = NULL
ingestion_tasks.error_message = NULL
```

如果任务已经是 `processing`、`completed` 或 `failed`，worker 不会重复认领。

### 7.3 实际导入

worker 完成以下操作：

1. 从 MinIO 下载到临时目录。
2. 确保 Milvus collection 存在。
3. 删除该文档旧的向量数据，避免重复导入。
4. 优先调用 MinerU 解析。
5. MinerU 失败时回退到 LlamaIndex。
6. 按 `CHUNK_SIZE` 和 `CHUNK_OVERLAP` 切块。
7. 调用 Embedding 模型生成向量。
8. 将分块、元数据和向量批量写入 Milvus。
9. 删除本地临时文件。

Milvus 每个分块至少包含：

```text
id
knowledge_base_id
doc_id
doc_name
doc_type
category
page_number
chunk_index
text
embedding
```

### 7.4 成功状态

导入成功后：

```text
documents.status        = completed
documents.chunk_count   = 实际写入的分块数
documents.error_message = NULL

ingestion_tasks.status        = completed
ingestion_tasks.error_message = NULL
ingestion_tasks.finished_at   = 当前 UTC 时间
ingestion_tasks.updated_at    = 当前 UTC 时间
```

### 7.5 失败状态

任意解析、Embedding、Milvus、MinIO 或其他导入环节抛出异常时：

```text
documents.status        = failed
documents.error_message = 错误信息

ingestion_tasks.status        = failed
ingestion_tasks.error_message = 错误信息，最多 2000 字符
ingestion_tasks.finished_at   = 当前 UTC 时间
ingestion_tasks.updated_at    = 当前 UTC 时间
```

初次导入失败时，`documents.chunk_count` 通常仍为 `0`。

### 7.6 状态查询

当前没有单独的任务查询接口。通过文档详情查询任务状态：

```text
GET /api/v1/documents/{document_id}
```

文档详情会同时返回：

```text
status
chunk_count
error_message
task_id
task_status
task_error_message
task_started_at
task_finished_at
```

文档列表接口只查询文档记录，不加载任务记录，因此列表中的任务字段可能为空。

## 8. API 说明

### 8.1 健康检查

```http
GET /api/v1/health
```

检查 PostgreSQL、MinIO bucket 和 Milvus。全部正常返回：

```json
{"status": "ok"}
```

依赖不可用时返回 `503`，不暴露底层异常细节。

### 8.2 知识库接口

```http
POST   /api/v1/knowledge-bases
GET    /api/v1/knowledge-bases
GET    /api/v1/knowledge-bases/{knowledge_base_id}
PUT    /api/v1/knowledge-bases/{knowledge_base_id}
DELETE /api/v1/knowledge-bases/{knowledge_base_id}
```

知识库删除采用保护策略：只要存在文档，就返回 `409`，不会级联删除文档。

### 8.3 文档接口

```http
POST   /api/v1/knowledge-bases/{knowledge_base_id}/documents
GET    /api/v1/knowledge-bases/{knowledge_base_id}/documents
GET    /api/v1/documents/{document_id}
DELETE /api/v1/documents/{document_id}
```

文档删除只允许 `completed` 或 `failed` 状态。删除时按顺序清理 Milvus 向量、MinIO 原文件、`ingestion_tasks` 记录和 `documents` 记录。

### 8.4 Chat 接口

```http
POST /api/v1/chat
```

请求示例：

```json
{
  "knowledge_base_id": "知识库 UUID",
  "question": "什么是 Transformer？",
  "role": "patient",
  "top_k": 20,
  "rerank_top_k": 5,
  "use_hyde": true
}
```

服务层先校验知识库，再使用 `knowledge_base_id` 过滤 Milvus 检索结果，避免跨知识库召回。

## 13. 删除行为和一致性边界

### 13.1 删除知识库

知识库下存在文档时返回 `409`，不会级联删除文档、导入任务、MinIO 对象或 Milvus 向量。必须先删除文档。

### 13.2 删除文档

文档处于 `pending` 或 `processing` 时返回 `409`。文档处于 `completed` 或 `failed` 时，服务层依次删除 Milvus 向量、MinIO 原文件、`ingestion_tasks` 记录和 `documents` 记录。

PostgreSQL、MinIO 和 Milvus 之间没有跨系统事务。外部清理失败时，数据库事务会回滚，但已经成功执行的外部删除无法由 PostgreSQL 回滚恢复。

## 14. 已知限制和维护建议

- 上传接口会把整个文件读入内存，尚未实现流式上传和大小限制。
- FastAPI `BackgroundTasks` 运行在 API 进程内，不是持久化任务队列；进程异常可能留下 `pending` 任务。
- 当前没有任务重试次数、重试接口、进度百分比和独立任务查询接口。
- 任务状态通过 `GET /api/v1/documents/{document_id}` 查看。
- 数据库模型不声明外键，关联完整性由服务层代码维护。
- 文档列表接口不会加载任务详情，任务字段可能为空。
- MinerU 和 LlamaIndex 都不可用时，导入任务会进入 `failed`。
- 模型服务、MinerU、Milvus 等真实集成测试会产生网络依赖或调用成本。
- `docker-compose.yaml` 中的 Neo4j 当前由基础设施提供，但 API 代码尚未使用。
